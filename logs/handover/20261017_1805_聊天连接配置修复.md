## 问题

运行日志里决策请求全部发往座位配置的中转地址（200），聊天请求全部发往 `https://api.openai.com/v1/chat/completions`（401）。原因：`chat_engine.trigger_event_chat` 调用网关时只传了 `provider` / `model` / `api_key`，没有传 `base_url`，网关落回 OpenAI 官方默认地址；中转站的 Key 因此被发给了官方服务器（被拒绝）。

同时，开场白在 `_run_phases` 之后才触发，并且直接 `await`：每次失败卡住主循环约 1.1 秒，若请求成功则要卡满模型思考时间（Stage T 方案 P2、P3）。每次失败还打印完整 traceback。

## 行为变化

1. **聊天与决策共用同一份连接配置**：新增 `ai_decision.model_call_kwargs(player)`，返回 provider / model / api_key / base_url（`api_url` 优先，兼容 `base_url`）。决策 `_call_with_session` 与聊天都从这里取，以后不会再分叉。
2. **聊天配置错误只提示一次**：HTTP 401 / 403 / 404，或网关报配置不可用（如 claude/gemini 未填兼容地址）时，本局停用该座位的聊天，只写一行警告（不打印堆栈、不含 Key）；429、超时等临时错误不停用。决策不受影响，仍走原有失败降级。
3. **开场白不再阻塞对局**：移到回合开始（`_run_phases` 之前）发起，用 `_spawn_chat` 作为后台任务运行；对局结束时 `_cancel_chat_tasks` 统一取消；结果回来时对局已结束则丢弃。30% 随机触发和 8 秒冷却保持原样（D2 的冷场检测留给 T3）。
4. **Stage T 方案第二次校准**：按 `e506961` 现状改写第 3、10.8、11、15、17、19、20 节，新增第 21 节"真实运行日志观察"。主要结论：P6/P7/P8、L1/L2/L3、死亡奖惩已完成；T0 只剩 P1、P5、`kind` 字段，新增 T0-7（摸牌/判定迁到 `move_card`）、T0-8（日志可读性）；新增待确认 H（真人阵亡后中止是否清连胜）、I（技能多步选择合并为一次决策）。
