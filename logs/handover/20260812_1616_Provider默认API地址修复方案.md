# Provider 默认 API 地址修复方案

## Aim（总目标）
恢复大厅选择 Provider 后自动填充其内置 API 地址和默认模型，并保持 `game_engine/protocol.py` 为 Provider 元数据唯一真相源。

## Objective（可验收目标）
1. 默认 Provider 的 API 地址不为空且不出现 `undefined`。
2. 切换到通义千问、OpenAI、DeepSeek 时，API 地址和模型与 `protocol.PROVIDERS` 一致。
3. `/api/providers` 成功及 `Protocol.PROVIDERS` 回退路径使用相同 snake_case 契约。
4. 聚焦测试与完整回归通过，真实浏览器完成默认值和切换验证。

## Risk（风险与对策）
- 风险：浏览器缓存旧 `lobby.js`。对策：更新 `index.html` 的静态资源版本参数并在验收时禁用缓存。
- 风险：误改协议或服务端以兼容 UI。对策：只修前端消费端，不修改 `protocol.py`、生成器、`MainEngine.providers()` 或 `/api/providers`。
- 风险：回归测试只验证上游字段而未约束消费端。对策：增加大厅源码契约测试，禁止重新引入 `defaultUrl/defaultModel` 死键。

## Change（改动清单）
- `frontend/js/lobby.js`：将 `defaultUrl/defaultModel` 读取统一为 `default_url/default_model`。
- `frontend/index.html`：更新 `lobby.js` 查询版本，确保浏览器获取修复脚本。
- `tests/test_protocol_sync.py`：新增大厅 Provider 字段消费契约测试。
- `logs/handover/`：完成后记录实际改动、真实命令输出和验收结论。
- `logs/CHRONICLE.md`：追加本次交接索引。

## Stages（阶段）
1. 固化方案与基线。
2. 修改大厅 Provider 字段读取及缓存版本。
3. 补充回归测试。
4. 运行聚焦测试、完整测试和前端语法检查。
5. 启动真实服务器，在浏览器验证默认 Provider、通义千问、OpenAI、DeepSeek切换。
6. 形成交接日志并更新 CHRONICLE 索引。

## 明确不在本次范围
聊天 Provider、全局设置语义、游戏内 AI 设置和后端聊天配置接线属于独立问题，本次不扩展处理。
