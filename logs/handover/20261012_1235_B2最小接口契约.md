# B2 最小接口契约（设计稿，尚未施工）

基线：`7b0f693e9def5c63802be84e2e3b53645039d944`；前置：B1 请求 ID、即时回执和结束门控。此文件冻结下一批跨引擎与旧 UI 的数据语义，不代表运行时已具备下列全部能力。

## 1. 交互请求

保留 `MainEngine.request_response/request_choice/ask_*` 门面。下一批内部请求对象至少含 `game_id`、`request_id`、`player_id`、`kind`、`candidate_version`、`selection`（`min/max/cancelable/zone`）、`options`、`timeout`。`game_id` 和 `request_id` 已在 B1 下发；`candidate_version` 尚未实现，必须来自本次候选快照，而非客户端自报。

提交仍用 `player_action` 的 `type=response`，附 `request_id` 与 `option_index`（单选）或 `option_indices`（多选）。B1 即时 `action_result` 回执的 `status` 为 `accepted/invalid/duplicate/stale/game_ended`，`accepted` 仅表示当前等待器接收输入；效果是否生效由请求解析与牌区复核决定。B2 将最终结果单独表达为 `resolved/cancelled/timeout/stale/invalid/game_ended`，不得把空列表同时用于取消、超时和结束。超时后规则托管沿用同一候选快照与复核；结束不得进入托管。已应答请求再次提交为 `duplicate`，过期请求不能命中下一请求。

一个请求只能有一名指定玩家应答；所有候选均按该玩家视角序列化。`Card` 不通过通用 `context` 下发；公开牌可放到明确的公开候选字段，隐藏手牌只给占位。Future 与处理器对象只保存在运行中请求表，`serialize()` 不包含它们。下一批先迁移弃牌阶段一个普通选牌消费者，再迁移一个技能选择；真人、模型、规则托管都调用同一最终复核函数。

## 2. 牌移动与事件

每次实体牌移动记录：`card_id`、`from_owner/from_zone`、`to_owner/to_zone`、`reason`、`actor_id`、`effect_id`、`visibility`、`sequence`。牌区以 `deck/hand/equipment/judge/discard/shown/temporary` 起步；临时展示或暂存仍保有唯一归属。一个移动先验证来源与目标，再一次提交，之后通知统计与技能监听；通知都读同一事件。统计按口径筛选，监听按技能规则筛选，不通过省略事件来修正统计。

首批真实消费者：弃牌阶段的手牌→弃牌堆；谦逊的手牌→暂存→返回手牌；一处使用牌造成的 `cards_played/cards_lost` 统计。谦逊的版本文本与“移出手牌”时机先核对；明确暂存语义后才决定哪些监听触发，不能沿用目前“完全不发失牌事件”的临时补丁作为通用规则。虚拟牌保留实体成本牌 ID 和技能来源，效果仍进入同一结算入口。

## 3. 技能状态

技能实例字段：`owner_id/skill_id/version_id/source/enabled/charges/usage_scope/usage_count/state`。`usage_scope` 至少有阶段、当前角色回合、整轮、整局；“自己的回合”与“任意角色的回合”分别建键。转换态、觉醒态和限定次数存在可序列化状态中，不能由通用回合清理清零。获得、失去、暂时禁用和恢复走同一生命周期接口，多来源同名技能按来源引用数处理。

首例选择：`制衡`作每回合次数技能；`替身`作整局次数检查；`勤学`作觉醒状态；不在本批一次迁移全部技能。每个首例需有正常、拒绝、取消和跨回合恢复证据；可选技能由真人决定，限定次数仅在效果确认后消耗。

## 4. 结算上下文与施工边界

一次效果上下文保留使用牌、来源、当前目标、伤害属性、已取消目标、待处理事件、中止原因和递增序号。先让普通牌与一个技能牌共用该入口，再迁移决斗及群体锦囊；无懈链不加深度上限。取消和结束在每个等待点返回明确原因，消费者检查后才能移动牌、造成伤害或发动画。

B2 只实现上述代表场景实际使用的接口，不添加没有消费者的通用类。老接口仅在仍有调用方时保留适配；待调用方迁完删除。B3 的决斗、群体锦囊、伤害、死亡和 B4 的装备机制依赖这里的请求及移动事实语义。
